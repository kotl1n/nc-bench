Данный документ фиксирует все методологические, лингвистические и технические решения, принятые в ходе русскоязычной адаптации бенчмарка разговорной компетентности **IBM NC-Bench**.

## 1. Фундаментальные принципы адаптации

1. **Сохранение проверяемого разговорного действия (Conversational Action)**:
   - Бенчмарк опирается на конверсационный анализ (Conversation Analysis, CA; Schegloff, Sacks, Jefferson). Главным объектом оценки является не формальный перевод слов, а **прагматическая функция реплики**:
     - **RepeatRequest** (устранение сбоя слышимости): «Что вы сказали?», «Повторите» — требует дословного повтора.
     - **ParaphraseRequest** (устранение сбоя понимания): «Что вы имеете в виду?», «Я не понял» — требует перефразирования другими словами.
     - **Sequence Closer** («Понял», «Ясно», «Спасибо», «Хорошо»): завершение темы, приглашение модели подтвердить закрытие (PreClosing/Silence), а не открывать новую тему.
     - **Sequence Abort** («Неважно», «Забудьте», «Отбой»): отмена диалоговой ветки.
     - **Self-Correction**: самоисправление пользователя («Нет, я имел в виду...») с сохранением контекстной неоднозначности.
2. **Запрет на подсказки и упрощения**:
   - Ни одно задание не упрощено и не снабжено дополнительными контекстными подсказками.
3. **Строгая симметрия структуры**:
   - Сохранены все 720 заданий: Basic (180), RAG (180), Complex Request (360).
   - Сохранены оригинальные числовые идентификаторы `id` (0..179, 0..179, 0..359), маппинг `original_id -> ru_id`, категории и распределение.

## 4. Обнаруженные и задокументированные особенности upstream IBM NC-Bench

В ходе тщательного анализа кодовой базы IBM NC-Bench были выявлены следующие архитектурные особенности и расхождения:

### 4.1. Ошибка подстановки слотов судьи в `utils.py`
- **Проблема**: В оригинальном коде `utils.generate_judge_prompts()` проверка заземлённых деталей выполнялась по объекту ответов модели:
  ```python
  if 'request_details' in response_entry:
      request_details = response_entry['request_details']
  else:
      request_details = ''
  ```
  Однако `generations_file` формируется скриптами генерации (`pred_hf.py`, `pred_gpt4o.py`), которые сохраняют только `id`, `task`, `output`. Поле `request_details` присутствует исключительно в исходном файле `prompts_file` (`chat_entry`)!
  В результате в оригинальном коде плейсхолдер `<request_details>` в инструкциях судьи **всегда заменялся на пустую строку `""`**, лишая судью информации о том, какие именно слоты считаются grounded.
- **Исправление**: В `utils.py` и `utils_ru.py` добавлена корректная цепочка:
  ```python
  request_details = response_entry.get('request_details') or chat_entry.get('request_details', '')
  ```

### 4.2. Ограничение оценки только первой строкой (`first_line`) и его устранение
- **Проблема в upstream**: В `utils.py`:
  ```python
  first_line = response_entry['output'].split('\n')[0].strip()
  ```
  Судья получал **только первую строку** генерации модели. Это прямо нарушало Правило 2 системного промпта судьи (*«Если ответ [AGENT] содержит несколько предложений, вы должны классифицировать каждое предложение»*) и ломало оценку ответов с переносами строк, приветствиями или Chain-of-Thought рассуждениями.
- **Исправление**: В `utils.py`, `utils_ru.py`, `judge_hf.py` и `judge_gpt4o.py` дефолтным режимом сделана полная передача ответа с нормализацией внутренних переносов строк в единую связную реплику:
  ```python
  agent_turn_text = " ".join([line.strip() for line in raw_output.splitlines() if line.strip()])
  ```
  Для воспроизведения старого поведения добавлен флаг `--truncate_first_line` (по умолчанию `False`).

### 4.3. Обработка пропущенных/неполных заданий в оценке и агрегации
- **Проблема в upstream**: В оригинальном коде генерация промптов судьи строилась только для `task_id in chat_data if task_id in response_data`. Если модель ответила только на 1 задание из 180, судья оценивал 1 задание, а агрегатор вычислял `ratio = score / count = 1 / 1 = 100%`, формируя вводящий в заблуждение отчёт о 100% точности.
- **Исправление**:
  1. В `utils.py` и `utils_ru.py` добавлен параметр `include_missing=True` (по умолчанию включён, отключается флагом `--ignore_missing`). Все задания из тестового набора передаются судье; для пропущенных заданий формируется реплика `[empty]` с флагом `is_missing: True` (по правилу 3 промпта судьи классифицируется как `Silence`).
  2. В `aggregator_ru.py` пропущенным ответам (`is_missing: True`) выставляется `score = 0` (даже в категориях Closer/Abort выпадение не премируется).
  3. Агрегатор принимает `--prompts_file` (или автоопределяет ожидаемое количество 180/360 по категориям) и рассчитывает две независимые метрики:
     - `evaluated_accuracy`: точность на фактически отвеченном подмножестве;
     - `benchmark_accuracy`: истинная точность бенчмарка с учётом штрафа за пропуски (`score / expected_instances`).
     - При наличии пропусков выдаётся предупреждение `INCOMPLETE EVALUATION WARNING`.

### 4.4. Строгая программная верификация датасета (`scripts/verify_dataset.py`)
- В первой версии скрипта верификации `all_pass2_ok` не переключался в `False` при обнаружении расхождений.
- Скрипт полностью переработан:
  - Автоматически находит корень репозитория независимо от текущей рабочей директории.
  - Поддерживает токенизацию акцентированных символов Unicode (французская типографика `Comédie-Française`), римских цифр (`XIV`, `XX`) и буквенно-цифровых кодов моделей (`S21`, `M1`, `401(k)`, `OBD-II`).
  - При обнаружении любого непредусмотренного латинского слова или отсутствующего числа флаг `all_pass2_ok` сбрасывается в `False`, и скрипт завершается с кодом возврата `1` (`sys.exit(1)`).

### 4.5. Расхождение параметров: скрипты vs научная статья
- **В статье (Moore et al., 2026)**:
  - Жадное декодирование (`temperature=0.0`, `do_sample=False`).
  - Лимит токенов генерации: **1024** токена.
  - Основной судья: `Mistral-Large-Instruct-2411` (валидирован на человеческой разметке, $\kappa = 0.899$).
- **В скриптах репозитория**:
  - Дефолтный `max_new_tokens`: **128** токенов.
  - Предлагаются модели `Llama-3.3-70B-Instruct` или `gpt-4o-2024-08-06`.

### 4.6. Пустые начальные реплики пользователя в Basic
- Примеры ID 1, 5, 6, 15, 85, 88 содержат пустую реплику `user: ""` в первой позиции диалога. Это вызвано тем, что в оригинальном диалоге первым начинает говорить ассистент, а стандартный чат-шаблон (chat template) требует чередования `user -> assistant`. Это поведение полностью сохранено в RU для 100% совместимости с chat template.

### 4.7. Аномалия Complex Request ID 340
- В оригинальном датасете IBM задание ID 340 (категория `Self-Correction`, персона 0 — консьерж) содержит лишнюю реплику `assistant` в конце диалога:
  `user -> assistant -> user -> assistant`.
  Во всех остальных 359 заданиях последней репликой является `user`. Данная особенность upstream сохранена bug-for-bug для воспроизводимости, но задокументирована.
